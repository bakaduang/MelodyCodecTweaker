# 切歌时音轨销毁修复 preview.7

版本：`2.5.0-preview.7`，versionCode `34`。用户已确认 preview.6 的单耳合并有效；本版处理切歌后播放服务重启、下一首停住并回到上一首的问题。

## 反馈与定位

`OPlusHeadsetAudioHelper-feedback-20260911-003403/logcat-bluetooth-root.txt` 显示：

- 00:33:37，QQ 音乐播放服务从 PID 30860 更换为 32128，再次加载模块。
- 00:33:48.095，新音轨 176 启动；00:33:48.223，旧音轨 175 停止并清空。
- 00:33:48.690，播放服务又以 PID 32730 启动，模块重新安装 Hook。与切歌后播放状态丢失的现象吻合。

音频库 Build ID 仍为 `e5ed64db3ed9ddca14c494145a509ee6`。反汇编定位到模块自身的一处 ABI 错误：`AudioTrack` 基类析构 D2 除了 `this`，还需要隐藏的 VTT 指针；preview.6 的包装函数仅转发了 `this`。

| 真机机器码位置 | 证据 |
| --- | --- |
| D1 `0xb98f8–0xb9904`、D0 `0xb992c–0xb9938` | 将 VTT 放入 x1，再调用 D2 |
| GOT `0x112558` | 重定位到 `_ZTTN7android10AudioTrackE` |
| D2 `0xb9dcc`、`0xb9dd8` | 分别读取 `[x1]` 与 `[x1+0x18]` |
| preview.6 wrapper `0x302cc–0x30304` | 只保存 this，清理模块音轨记录后未恢复 x1 就跳到原析构函数 |

这会使旧音轨销毁时使用已破坏的 VTT。它符合 [Itanium C++ ABI 的 VTT 参数规则](https://itanium-cxx-abi.github.io/cxx-abi/abi.html#vtt-parameters)：带虚基类的基类构造/析构有第二个隐式参数，而该参数不会出现在普通反修饰结果中。[ARM64 C++ ABI](https://github.com/ARM-software/abi-aa/blob/main/cppabi64/cppabi64.rst) 沿用这一参数规则。

反馈未包含原始 native crash backtrace，因此没有把某个具体信号或崩溃地址当成已捕获的真机事实。错误由真实库与已发布模块的机器码确认；进程重启时间与触发路径吻合。

## 修改与验证

1. D2 使用独立的双参数函数类型，跨模块记录清理保留并原样传递调用者的 VTT；D0/D1 继续使用其单参数 ABI。不会自行替换成某个固定 VTT。
2. 拒绝 D2 与 D0/D1 共用同一地址的未知情况，避免复用参数列表不同的包装函数。当前真机库的三个入口地址各不相同。
3. 为诊断记录补充 `libc:F`、`DEBUG:F`、`AndroidRuntime:E`，后续 native/Java 崩溃可以保留具体错误与回溯。

新增回归测试使用编译器生成的真实虚继承析构函数，连续构建、释放并复用 512 个音轨模型，检查 VTT 转发和虚基类销毁次序。修复版通过；重现旧版漏参调用的对照版按预期失败，且在解引用错误指针前报告失败。最终 ARM64 包装函数已核对：`0x302e8` 将 x1 保存到 x19，调用清理后，在 `0x30308` 将 x19 恢复到 x1，再跳转系统析构函数。

本次保留已经实机生效的 PCM 合并方式，不涉及播放器播放列表、上一首/下一首按钮或音乐文件。本地析构测试和构建不能代替真实播放器的切歌复测。

## 安装后验证

覆盖安装并重启手机，然后分别在 QQ 音乐、网易云音乐中验证：

- 单耳合并开启，连续切换多首歌曲，包含播放中切歌、暂停后切歌及不同采样率的歌曲。
- 等待一首自然结束，确认下一首正常播放；再测试暂停、继续和上一首。
- 确认单耳仍能听到左右声道，双耳恢复立体声。

若仍出现异常，保持诊断记录开启后复现一次，再生成反馈。新日志已加入崩溃回溯的采集。此前的入口与加载适配见 [preview.6 说明](player-pcm-preview6.md)。
